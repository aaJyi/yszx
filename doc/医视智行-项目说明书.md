# 医视智行——基于机器视觉的多智能体医疗问诊康复辅助诊疗系统  
## 项目说明书

- `backend`（Spring Boot + MyBatis-Plus 主后端）  
- `backend-PC`（Vue3 管理后台）  
- `fronted-mini`（uni-app 小程序前端）  
- `ai-doctor-rag`（中英文 RAG 医学问答服务）  
- `ai-exercise-train`（运动识别与动作计数服务）  
- `food-train`（三餐图像营养识别服务）  
- `club-division`（NCSS 社团划分算法实现）  
- `backend/scripts/social`、`backend/scripts/organ_disease_crawl`（热点疾病抓取与知识更新）

## 1. 项目概述

### 1.1 项目名称
医视智行——基于机器视觉的多智能体医疗问诊康复辅助诊疗系统

### 1.2 建设背景
当前我国慢病年轻化趋势明显，大学生群体在“亚健康、心理压力、运动不足、饮食失衡、健康信息过载”方面问题突出。传统就医流程存在“轻症过度就医”和“风险症状延迟就医”并存现象，基层医疗咨询能力与个体健康管理需求之间存在长期错配。  
在此背景下，本项目以“低门槛、高可及、可持续追踪”为目标，构建多智能体协同架构：通过小程序端采集用户日常健康数据，以视觉识别（运动、三餐）+ 智能问答（中英文 RAG）+ 疾病风险推测 + 热点知识更新 + 社群分层干预（NCSS）形成闭环，支持“日常管理—风险提示—辅助决策—持续康复”全链路。

### 1.3 建设目标
- 面向用户：提供可解释、可追踪、可落地的健康辅助服务。  
- 面向运营：提供后台数据总览、知识库管理、社群划分与干预工具。  
- 面向赛事：形成“算法 + 系统 + 工程 + 应用 + 社会价值”完整参赛成果。  
- 面向交付：具备模块化部署能力，支持后续增量接入英文问答 RAG 与三餐识别模型。

### 1.4 核心创新点
- 多智能体协同：问诊、知识检索、视觉识别、社群推荐、热点爬虫统一编排。  
- 中英文 RAG 融合：支持中文医疗问答与英文语料补充，提升复杂场景召回覆盖。  
- 机器视觉双模型：运动识别与饮食识别分别建模，服务康复与营养双路径。  
- NCSS 社团划分落地：从论文算法到业务系统，形成“同病互助 + 精准干预”机制。  
- 可运维化：后端/管理端提供向量重建、知识维护、数据回溯、资产可视化能力。

## 2. 需求分析说明书

### 2.1 功能性需求
- 智能问诊：支持多轮对话，具备 RAG 检索证据与回答可解释性。  
- 中英文知识接入：支持中文主检索 + 英文扩展知识索引。  
- 运动识别：图像/视频识别运动类型，支持计时、计次、会话统计。  
- 三餐识别：图像识别营养指标（热量、宏量营养素）用于饮食建议。  
- 疾病推测与建议：结合用户历史与行为数据生成风险提示与建议。  
- 社团划分与推荐：通过 NCSS 识别相似健康群体，支持同类交流与干预。  
- 热点疾病抓取：自动抓取时事疾病资讯并入库，为问答与推荐提供增量数据。  
- 后台管理：用户、知识库、图谱、文章、数据概览、模型维护等管理能力。

### 2.2 约束与边界
- 系统提供“辅助诊疗”能力，不替代临床医生诊断。  
- 医疗回答需附风险提示与免责声明。  
- 对于高风险症状，必须引导线下就医。

## 3. 设计思路

### 3.1 设计目标与方法论
本系统采用“业务闭环优先、技术分层落地、智能体协同增强”的总体方法论。目标不是单点模型最优，而是在真实校园健康场景中实现可持续运行、可解释输出、可运维交付。  
总体目标：
1) 全链路闭环：采集 -> 分析 -> 建议 -> 反馈 -> 再优化；  
2) 模块可替换：模型升级不影响业务主链路；  
3) 故障可降级：任一智能体异常时主流程仍可用；  
4) 展示可评审：架构、接口、日志、指标一体化可说明。

### 3.2 分层架构思想
系统采用五层结构：
- 接入层：`fronted-mini`、`backend-PC`  
- 编排层：`backend`  
- 能力层：`ai-doctor-rag`、`ai-exercise-train`、`food-train`、`club-division`、爬虫脚本  
- 数据层：MySQL、Chroma、文件存储  
- 运维层：脚本调度、重建任务、监控告警

分层价值在于：交互变化、业务变化、算法变化、数据变化可以分开演进，避免一次改动牵一发动全身。

### 3.3 核心设计原则
1) 可解释优先：医疗回答尽可能有证据来源；  
2) 安全边界明确：输出“辅助建议”而非“确诊结论”；  
3) 异常优雅处理：统一错误码、重试策略与降级模板；  
4) 数据回流：所有关键结果可回写用于后续评估与优化。

### 3.4 主业务时序总纲
统一时序：  
前端请求 -> `backend` 参数校验/鉴权 -> 调用目标智能体 -> 结果聚合 -> 数据回写 -> 前端展示。  
在实现层面，`backend` 负责超时控制、幂等控制、异常转换、调用日志，智能体服务聚焦能力输出。

### 3.5 异常流总纲
异常分为输入异常、业务异常、服务异常、数据异常。  
统一处理策略：  
- 可恢复异常：短重试 + 指数退避；  
- 不可恢复异常：立即降级 + 可读提示；  
- 关键失败：写告警日志并触发运维处理；  
- 医疗高风险：即使服务异常也要优先输出“线下就医提醒”兜底。

## 4. 系统框架构建（子系统详细说明，含接口时序与异常流）

### 4.1 小程序子系统（`fronted-mini`）
**职责**：承载用户触达、数据采集与结果展示，覆盖问答、识别、档案、社交等页面。  
**接口时序**：用户操作 -> 小程序请求 `backend` -> 后端调智能体 -> 返回聚合结果 -> 小程序展示与引导。  
**异常流**：网络失败时保留输入并提示重试；上传失败时支持重拍/压缩；服务超时时展示降级结果与重试按钮。

### 4.2 管理后台子系统（`backend-PC`）
**职责**：运营看板、知识管理、用户治理、图谱展示与策略配置。  
**接口时序**：管理员操作 -> 管理端请求后端 -> 后端执行统计/维护任务 -> 返回结果并刷新图表。  
**异常流**：鉴权失败跳转登录；重建任务失败展示日志摘要；数据为空展示空态模板；并发编辑冲突提示刷新。

### 4.3 业务后端子系统（`backend`）
**职责**：全局编排中心，统一鉴权、参数校验、服务调用、数据持久化、统一响应。  
**接口时序**：请求入站 -> DTO校验 -> Service编排 -> 调用外部AI服务 -> 数据入库 -> 返回标准结果。  
**异常流**：参数错误直接返回；依赖超时触发熔断降级；数据库失败回滚并记录；第三方异常进入补偿任务。

### 4.4 RAG问答子系统（`ai-doctor-rag`）
**职责**：检索增强问答，支持标准问答、流式问答、向量重建与热加载。  
**接口时序（标准）**：`backend` 调 `/chat` -> 检索召回 -> 相似度判定 -> 生成回答 -> 返回 references + answer。  
**接口时序（流式）**：`backend` 调 `/chat/stream` -> 先 `meta` -> 再 `chunk` -> 最后 `done`。  
**异常流**：索引缺失提示重建；模型不可用切换备选或仅检索模式；低相似度触发拒答/通用建议模板。

### 4.5 运动识别子系统（`ai-exercise-train`）
**职责**：输出运动类型、时长、计次，支持会话化跟踪与视频分析。  
**接口时序（图片）**：调用 `/recognize` -> 目标检测 -> 姿态计次 -> 会话统计 -> 返回结构化结果。  
**接口时序（视频）**：调用 `/recognize-video` -> 逐帧检测与稳定过滤 -> 汇总各动作统计 -> 返回报告。  
**异常流**：视频格式不支持即刻拒绝；姿态模型失败降级为仅识别类型；长视频超时改异步任务。

### 4.6 三餐识别子系统（`food-train`）
**职责**：对餐食图像做营养估计，提供饮食干预输入。  
**接口时序**：调用 `/predict` -> 图像解码 -> 模型推理 -> 返回营养结果 -> 后端写入建议链路。  
**异常流**：空文件/坏图直接返回参数错误；推理失败返回“预测失败”；模型缺失在启动阶段阻断服务。

### 4.7 社团划分与推荐子系统（`club-division` + `backend`）
**职责**：运行 NCSS 形成社团结构，支撑同类推荐和分层干预。  
**接口时序**：定时/手动触发划分 -> 读取用户特征构图 -> 输出社团入库 -> 在线按用户读取推荐。  
**异常流**：特征不足则标记待补全；计算失败回退到上一版本社团；在线读取失败降级规则推荐。

### 4.8 热点知识爬虫子系统（`backend/scripts/social` 等）
**职责**：抓取疾病热点资讯，清洗后入库，为问答和推荐提供时效性内容。  
**接口时序**：后端触发抓取 -> 多源检索 -> 清洗去重 -> 入库 -> 返回抓取数量。  
**异常流**：源站不可达时切换其他源；解析失败记录失败队列；低可信内容不入库；全链路失败保持旧内容服务。

### 4.9 子系统协同的统一异常策略
所有子系统遵循同一异常协定：  
1) 错误码分层（参数/业务/服务/系统）；  
2) 响应内含用户可读提示；  
3) 后端日志保留调用链路ID；  
4) 前端展示“可操作下一步”（重试、反馈、联系客服、线下就医）。

## 5. 智能体单独分析

### 5.1 智能健康建议与疾病推测智能体（Health Reasoning Agent）

#### 5.1.1 智能体定位
智能健康建议与疾病推测智能体是系统中的“决策层智能体”。它不直接替代医生诊断，而是基于用户档案、问答语义、行为数据（运动、饮食、睡眠等）形成风险分层和干预建议，最终输出“可执行的健康行动清单”。  
在产品价值上，该智能体承担三个核心职责：  
1) **风险早发现**：对潜在慢病风险给出早期提示；  
2) **建议可执行**：将抽象健康建议转化为“可落地任务”；  
3) **闭环可追踪**：建议产生后可在后续行为数据中验证效果。

#### 5.1.2 输入数据与特征体系
该智能体的数据输入来自四个维度：  
- **基础档案**：年龄、性别、既往病史、家族史、体重身高等；  
- **主诉对话**：用户在问答中的症状描述、持续时间、诱因、伴随症状；  
- **行为数据**：运动识别结果（三要素：类型、时长、次数）+ 饮食识别结果（热量、营养素）；  
- **系统上下文**：同类用户社团画像、近期健康热点、知识库证据片段。  

针对以上输入，系统构建“多源特征向量”，其本质是将不同数据模态映射为统一风险评估空间：  
- 文本特征：症状关键词、否定词、时间词、频度词；  
- 数值特征：BMI、运动总时长、平均热量、作息波动；  
- 结构特征：社团标签、相似用户风险密度、内容暴露频率。

#### 5.1.3 推测逻辑与建议生成机制
该智能体采用“规则先行 + 模型增强”的混合机制。  
第一层是规则引擎：用于保证医疗安全边界，例如“胸痛 + 呼吸困难 + 持续加重”直接触发就医提醒，不进入普通生活建议分支。  
第二层是语义模型与统计评分：对非紧急场景进行风险评分，输出低/中/高风险等级。  
第三层是模板化建议生成：根据风险等级和人群属性，生成生活方式建议、复查建议、就医建议三类内容。

建议输出不是一段空泛文字，而是结构化对象，包含：  
- 风险标签（如代谢风险、睡眠风险、情绪风险）；  
- 证据摘要（来自问答上下文与知识检索）；  
- 行动方案（本周执行、每日目标、复盘节点）；  
- 注意事项（危险信号出现时立即就医）。

#### 5.1.4 工程实现路径
在现有工程中，健康推测链路由 `backend` 服务完成编排：  
- 接收前端主诉与行为输入；  
- 调用 RAG 结果作为语义证据；  
- 汇总用户历史与规则策略；  
- 写入用户推测疾病与建议结果（如社交模块推测疾病链路）。  
随后可以由 `SocialAgentController` 触发后续流程：把推测疾病写入用户记录，再按疾病主题抓取热点资讯，实现“推测—内容供给”联动。

#### 5.1.5 可信性与安全设计
医疗类智能体的核心不在“回答多聪明”，而在“边界是否清晰”。本系统采用四层防护：  
1) **结论边界**：输出“风险提示/建议”，不输出“确诊”；  
2) **危险信号优先**：高危关键词触发强提醒与线下就医导流；  
3) **证据绑定**：建议尽量绑定检索证据，减少无依据输出；  
4) **审计回溯**：关键建议可追踪来源与触发条件，便于复盘。

#### 5.1.6 典型场景示例
场景A：用户长期疲劳、饮食不规律、运动不足。  
智能体输出：中风险代谢预警 + 每日步行目标 + 晚餐热量约束 + 两周复评。  
场景B：用户出现持续胸闷、夜间呼吸困难。  
智能体输出：高风险提示 + 立即就医建议 + 禁止延迟观察文案。  
场景C：用户仅为健康咨询，无明确症状。  
智能体输出：健康教育内容 + 预防型生活建议 + 打卡计划。

#### 5.1.7 评估指标与优化方向
建议建立以下指标体系：  
- 风险识别准确性（与医生复核或标准问卷对比）；  
- 建议采纳率（用户执行比例）；  
- 复评改善率（BMI、运动量、饮食指标变化）；  
- 安全事件率（高风险场景漏提醒率）。  
后续可引入“医生协同审核模式”和“建议效果在线学习”机制，进一步提升精度与可用性。

### 5.2 RAG中英文对话智能体（Medical RAG Agent）

#### 5.2.1 智能体定位
RAG 智能体是系统“知识中枢”。它解决两个关键问题：  
1) 如何让模型回答“有依据”；  
2) 如何在中英文知识混合条件下保持稳定问答质量。  
项目中该能力由 `ai-doctor-rag` 提供，具备标准问答与流式问答接口，支持向量重建和热加载。

#### 5.2.2 功能
根据 `ai-doctor-rag/app.py` 与 `rag_engine.py`，当前已具备：  
- `POST /chat`：标准问答；  
- `POST /chat/stream`：NDJSON 流式输出；  
- `POST /internal/rebuild-vector`：按数据集重建向量；  
- `POST /internal/reload-rag-index`：重载索引；  
- 支持中文 BGE-m3 集合、Chroma 持久化、Ollama/DeepSeek/本地模型切换。

#### 5.2.3 核心机制拆解
RAG链路可分为五步：  
**第一步：查询构建**  
系统会结合当前问题与对话历史构建检索查询，避免多轮对话中“追问跑偏”。  
**第二步：向量检索**  
对查询进行向量化，进入 Chroma 检索 Top-K 相关条目。  
**第三步：相关性判断**  
若最佳相似度低于阈值，则触发“Direct LLM”回退模式。  
**第四步：答案生成**  
将检索证据拼接到提示词中，调用目标模型生成回答。  
**第五步：安全收口**  
输出中加入“仅供参考、不构成诊断建议”等安全提示。

#### 5.2.4 中英文RAG融合策略
你后续将接入英文版 AI 问答 RAG，该方向与当前架构天然兼容。建议采用：  
- 中文主索引 + 英文补充索引双集合；  
- 查询语言检测后决定主检索集合；  
- 在罕见病、药物说明等场景启用跨语种补检索；  
- 最终回答统一中文输出，并保留英文证据引用片段。  
该策略可兼顾中文用户体验与英文医学资料覆盖能力。

#### 5.2.5 流式对话与体验设计
流式接口可显著改善用户感知延迟。  
在工程上，`/chat/stream` 先返回 `meta`（引用与相似度），再返回 `chunk`，最后 `done`。  
这种设计的价值在于：  
- 前端可先渲染“检索证据卡片”；  
- 用户知道答案来自哪里，信任度更高；  
- 失败时可在中途止损，避免长时间等待。

### 5.3 运动识别智能体（Exercise Vision Agent）

#### 5.3.1 智能体定位
运动识别智能体负责将“视频或图片输入”转化为“可用于健康管理的结构化运动记录”。  
在康复辅助场景中，光有“识别到在运动”不够，必须进一步输出：  
- 做了什么运动；  
- 做了多久；  
- 做了几次；  
- 动作执行是否稳定。  
这正是该智能体的工程价值所在。

#### 5.3.2 现有实现能力（对齐 `ai-exercise-train/run_server.py`）
当前服务支持：  
- `/recognize`：图片识别 + 会话化计次；  
- `/recognize-base64`：JSON传图场景；  
- `/recognize-video`：整段视频离线分析；  
- 可选姿态模型（启用后支持次数统计）；  
- 会话状态管理（`sessionId` 关联连续输入）。

#### 5.3.3 算法链路
运动识别使用“检测 + 姿态”双阶段：  
1) 检测模型判别运动类型；  
2) 姿态模型提取关键点；  
3) 通过角度阈值完成“上下状态转换”计次；  
4) 对连续帧进行稳定性过滤（`stable_frames`），抑制抖动误判；  
5) 对会话窗口进行时长累计与记录输出。  
这一设计适合面向真实使用环境（角度变化、遮挡、抖动、短时误检）。

#### 5.3.4 业务价值
该智能体不仅服务“健身记录”，更重要的是服务“康复处方执行追踪”：  
- 对术后康复、体态训练、慢病运动干预具有直接价值；  
- 能把用户执行情况转化为量化指标，辅助后续建议调整；  
- 在高校场景中可用于体测辅助与健康激励任务。

#### 5.3.5 工程难点与解决方案
难点一：单帧误检导致统计断裂。  
解决：引入稳定帧门限 + 会话状态机，避免频繁切换。  
难点二：计次误差大。  
解决：针对不同运动配置不同关键点与阈值（配置化）。  
难点三：真实环境噪声。  
解决：加入超时回收、动作延迟确认、失败兜底策略。

#### 5.3.6 指标体系
建议至少统计：  
- 运动类型识别准确率；  
- 计次误差（MAE）；  
- 时长误差；  
- 会话连续性成功率；  
- 实时响应帧率。  
在汇报中可展示“同一视频人工标注 vs 系统统计对比表”。

#### 5.3.7 后续优化路线
- 多人场景识别（目标跟踪 + 主体选择）；  
- 低功耗端侧推理（蒸馏/量化）；  
- 动作标准度评分（角度轨迹质量评估）；  
- 康复计划联动（动作完成度影响下阶段建议强度）。

### 5.4 三餐识别机器学习智能体（Diet Vision Agent）

#### 5.4.1 智能体定位
三餐识别智能体用于把“餐食图像”转化为“营养估计结果”，为健康建议提供饮食维度证据。  
它解决的是健康管理中长期存在的“饮食不可量化”问题：用户往往知道“要少吃油盐糖”，但不知道自己实际摄入是否超标。

#### 5.4.2 当前实现能力（对齐 `food-train/run_server.py`）
当前服务已经提供：  
- `POST /predict`：上传图片返回营养结果；  
- 轻量 FastAPI 部署；  
- 模型可替换（启动参数可指定模型路径）。  
该结构便于后续你接入新版本三餐识别模型，不影响上层业务接口。

#### 5.4.3 技术链路
流程为：  图像接收 -> 预处理 -> 模型推理 -> 结果结构化 -> 返回前端/后端。  
目前输出可作为“营养估计基础项”，进一步可在后端映射为：  

- 热量分级（低/中/高）；  
- 三大营养素比例偏差；  
- 饮食建议模板触发（增蛋白、减碳水、控脂等）。

#### 5.4.4 与健康建议智能体协同
三餐识别不能孤立使用，最佳方式是作为“健康建议智能体”的输入源：  
- 当连续多日高热量高脂饮食时，提高代谢风险权重；  
- 当运动量不足 + 高能量摄入叠加时，触发体重管理建议；  
- 在慢病人群（如高血压、高血脂）下，触发定制饮食提醒。  
这形成“行为证据驱动建议”的闭环逻辑。

### 5.5 热点疾病自动化爬虫智能体（Hot Disease Crawler Agent）

#### 5.5.1 智能体定位
热点疾病爬虫智能体负责“知识增量供给”，解决知识库时效性问题。  
在医疗场景中，信息过时会直接降低问答可信度，因此必须建立自动更新链路：  
热点发现 -> 内容抓取 -> 结构化清洗 -> 入库 -> 推荐/问答可用。

#### 5.5.2 当前工程基础
项目中已具备相关脚本体系：  
- `backend/scripts/social/*`：资讯聚合与源适配；  
- `backend/scripts/organ_disease_crawl/*`：器官疾病相关抓取与导入。  
并且后端中已有智能体触发入口，可按用户推测疾病触发文章刷新。

#### 5.5.3 工作流程
1) 根据疾病关键词发起多源抓取；  
2) 对返回内容做去重、清洗、摘要；  
3) 过滤低可信来源；  
4) 将合格内容写入业务库；  
5) 推送给相关用户或供问答检索使用。  
这条链路的重点在于“质量控制”，不是单纯抓取条数。

#### 5.5.4 质量控制机制
建议实施四项机制：  
- **可信度评分**：来源权威性、历史稳定性、内容一致性；  
- **时效性评分**：发布时间衰减函数；  
- **重复度控制**：标题相似度 + 正文向量相似度去重；  
- **风险过滤**：谣言词典、夸大疗效词、违规广告词过滤。  
这样可保证进入系统的资讯“可用、可读、可控”。

#### 5.5.5 与其他智能体的协同价值
爬虫智能体是“上游供给者”：  
- 为 RAG 提供新鲜知识；  
- 为社交推荐提供热点主题；  
- 为健康建议提供时事背景（季节性流行病等）。  
多智能体协同后，系统从“静态问答”升级为“动态健康信息服务”。

#### 5.5.6 法规与伦理注意点
资讯抓取必须强调：  
- 尊重版权与来源标注；  
- 对转载内容保留原文链接；  
- 不对非权威结论进行“确定性医学表述”；  
- 高风险内容需附提示并建议求医。  
这既是合规要求，也是甲方最看重的风险控制能力。

#### 5.5.7 评估与运维
建议维护以下运营指标：  
- 抓取成功率、入库通过率、去重率；  
- 资讯点击率、阅读完成率、转化率；  
- 与用户推测疾病匹配命中率；  
- 问答引用新资讯比例。  
当这些指标稳定后，项目即可形成“内容飞轮效应”。

## 6. NCSS社团划分算法扩写

### 6.1 研究背景与问题定义

在本项目中，社团划分并非“锦上添花”的推荐功能，而是连接“个体问诊”与“群体干预”的关键桥梁。仅依赖个体级别策略，会面临两个现实问题：  
1) 用户行为数据稀疏，单用户信息不足，建议稳定性差；  
2) 缺乏同类人群对照，难以做社群化运营和精准内容分发。  

因此，引入社团发现算法的目标是：在用户健康关联网络中找出“内部相似、外部差异”的群体，为内容推荐、同类交流、分层干预、活动组织提供结构基础。

形式化定义如下：  
- 给定用户集合 `V`，每个用户有疾病/症状标签集合；  
- 通过相似度规则构建无向图 `G=(V,E)`；  
- 寻找社团集合 `C={C1,C2,...,Ck}`，使得社团内关联更紧密，社团间关联更稀疏；  
- 同时要求算法在中大规模数据上可接受（工程复杂度可控）。

### 6.2 选择NCSS的原因

与传统全局算法相比，NCSS兼具精度与效率平衡。  
其核心思路是：  
- 先用全局信息（节点中心度）找到“可靠种子”；  
- 再用局部信息（结构关系强度 + 依赖度）进行社团扩张；  
- 最后进行小社团过滤，提升结果稳定性。  

这种“全局选种子 + 局部做扩张”的混合策略，恰好契合健康社群场景：  
- 可以减少随机初始化导致的不稳定；  
- 可以避免全局算法高复杂度导致的实时性问题；  
- 可以在不断新增用户时保持可维护性。

### 6.3 项目中的图构建方式（业务映射）

在 `NCSS.py` 中，图构建由 `build_user_similarity_graph` 完成：  
- 每个用户节点对应一个疾病集合；  
- 任意两用户用 Jaccard 相似度计算边权（当前实现为阈值后无权边）；  
- 当相似度超过阈值（如 `0.3`）时建立无向连接。  

该方式的工程优点：  
1) 计算直观，便于解释给非算法评委；  
2) 对标签缺失有一定鲁棒性；  
3) 可与后续多模态特征（行为、文本）兼容扩展。  

### 6.4 NCSS算法流程分解

#### 6.4.1 Step 1 构建相似网络
输入用户标签，输出邻接表结构 `adjacency`。  
复杂度约 `O(n^2 * s)`（`s` 与标签集合交并运算有关），在用户量增大时可用倒排索引优化。

#### 6.4.2 Step 2 共同邻居矩阵
`compute_common_neighbors` 计算任意节点对共同邻居数量，作为后续中心度与结构强度计算基础。  
共同邻居可理解为“拓扑层面的相似关系证据”。

#### 6.4.3 Step 3 节点中心度迭代
`compute_node_centrality` 采用类 PageRank 递推方式：  
- 节点中心度由邻居中心度贡献；  
- 贡献比例与共同邻居相关；  
- 通过阻尼系数与收敛阈值控制稳定性。  
这一步的目标是识别“潜在核心节点”，避免随机选种子。

#### 6.4.4 Step 4 种子节点筛选
`select_seed_nodes` 在工程上增加了三类约束：  
1) 中心度不低于均值；  
2) 度数不低于均值；  
3) 新种子与已有种子不直接相连（尽量覆盖不同社团）。  
这一步是 NCSS 相比普通局部算法稳定性更高的关键。

#### 6.4.5 Step 5 社团扩张与节点迁移
`community_expansion` 对每个社团边缘节点计算结构关系强度 `S(i,C)`：  
- 若强度为正，视为潜在可吸纳节点；  
- 对已归属他社团节点，再比较依赖度 `D(i,Cnew)` 与 `D(i,Cold)`；  
- 若新社团依赖度更高且超过阈值，则执行迁移。  
该机制对应“先吸纳、再校正”的迭代过程。

#### 6.4.6 Step 6 小社团过滤
`filter_small_communities` 将过小社团并入最大社团，提升结果业务可用性。  
在健康管理场景中，小社团可能噪声较大、运营价值低，因此该步骤有明确产品意义。

### 6.5 解释

#### 6.5.1 节点中心度
中心度项可理解为“节点在整体网络中作为核心的概率权重”。  
工程意义：避免把边缘节点误选为种子，从源头降低错误扩张风险。

#### 6.5.2 节点对社团依赖度
依赖度本质是“某节点邻居中有多少比例落在该社团”。  
工程意义：为节点迁移提供定量依据，防止社团边界反复震荡。

#### 6.5.3 节点对社团结构关系强度
强度衡量节点与社团在拓扑结构上的“净吸引力”。  
工程意义：决定扩张方向，不再仅凭局部度或单一相似度。

三者组合形成 NCSS 的核心闭环：  
**中心度选种子 -> 强度做扩张 -> 依赖度做修正**。

### 6.6 NCSS伪代码（可直接插入说明书）

```text
Algorithm NCSS-Community-Detection
Input:
  UserDiseaseMap U
  similarity_threshold τ
  damping_factor c
  dependency_threshold δ
  epsilon ε
Output:
  Communities C

1.  Build graph G=(V,E) by Jaccard(Ui, Uj) > τ
2.  Compute common-neighbor matrix CN
3.  Initialize PRcen(v)=1/|V| for each v in V
4.  Repeat until convergence:
      For each node v:
        PRnew(v) = c * Σ_{u∈N(v)} PRcen(u) * weight(u,v) + (1-c)/|V|
      If max|PRnew-PRcen| < ε: break
      PRcen ← PRnew
5.  Select seed set S with constraints:
      PRcen(v) >= avg(PRcen), degree(v) >= avg_degree
      and v not directly connected to existing seeds
6.  Initialize each seed as one community
7.  Repeat:
      For each community Ci:
        Collect boundary candidates Bi
        For each node x in Bi:
          Compute structural strength Score(x,Ci)
        Select best x* with Score>0
        If x* unassigned: add x* to Ci
        Else:
          let Cj be old community of x*
          If Dep(x*,Ci) > Dep(x*,Cj) and Dep(x*,Ci) > δ:
             move x* from Cj to Ci
   until no node changes
8.  Dissolve too-small communities and merge into largest one
9.  Return C
```
