# 会诊功能实现建议

本文档结合当前会诊前端页面（`fronted/pages/medical-service/consultation.vue`）与项目技术栈，给出**会诊表设计**与**小程序会诊功能实现**的完整建议，便于后续开发且有利于用户使用。**仅作建议，不直接修改代码。**

---

## 一、当前前端会诊流程与数据概览

| 步骤 | 内容 | 涉及数据 |
|------|------|----------|
| 1. 选择类型 | 线上会诊 / 线下会诊 | `selectedType`: online / offline |
| 2. 填写信息 | 疾病信息、会诊需求、病历附件、联系电话 | `form`: diseaseType, conditionDesc, pastHistory, treatmentPlan, consultPurpose, expectedTime, phone；附件最多 10 张 |
| 3. 选择专家 | 按科室筛选，多选专家（最多 5 位） | `selectedDepartment`, `selectedExperts[]`（id, name, title, hospital, specialty） |
| 4. 确认提交 | 汇总信息、费用、提交 | 费用：基础 1500 + (专家数-1)×500 |

后端已有 `real_doctor` 表与医生列表/详情接口，会诊专家可从该表选取或扩展。

---

## 二、会诊表设计建议

### 2.1 主表：会诊申请/会诊单（建议表名：`mdt_consultation` 或 `consultation_order`）

用于存一条会诊申请（对应前端一次「确认提交」）。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | BIGINT AUTO_INCREMENT | 主键 |
| order_no | VARCHAR(32) | 会诊单号（唯一，便于用户查询、客服沟通） |
| user_id | BIGINT | 申请人用户 ID（关联 t_user） |
| consultation_type | TINYINT / VARCHAR(10) | 会诊类型：1-线上 / 2-线下（与前端 selectedType 一致） |
| disease_type | VARCHAR(100) | 疾病类型 |
| condition_desc | TEXT | 病情描述 |
| past_history | TEXT | 既往病史（选填） |
| treatment_plan | TEXT | 当前治疗方案（选填） |
| consult_purpose | TEXT | 会诊目的 |
| expected_time | VARCHAR(100) | 期望时间（选填） |
| contact_phone | VARCHAR(20) | 联系电话 |
| base_fee | DECIMAL(10,2) | 基础费用（如 1500） |
| extra_fee_per_expert | DECIMAL(10,2) | 每增加一位专家的加价（如 500） |
| expert_count | INT | 参与专家数量 |
| total_fee | DECIMAL(10,2) | 总费用（便于订单与对账） |
| status | TINYINT / VARCHAR(20) | 状态：待审核/待支付/待排期/已排期/已完成/已取消 等（见下） |
| scheduled_at | DATETIME | 实际会诊时间（排期后填） |
| create_time | DATETIME | 创建时间 |
| update_time | DATETIME | 更新时间 |
| remark | VARCHAR(500) | 备注（客服/运营用） |

**建议索引**：`user_id`、`order_no`（唯一）、`status`、`create_time`。

**状态枚举建议**（可与产品再对齐）：

- 0 或 draft：草稿（若支持保存未提交）
- 1 或 pending_review：待审核
- 2 或 pending_payment：待支付
- 3 或 pending_schedule：待排期
- 4 或 scheduled：已排期（含 scheduled_at）
- 5 或 completed：已完成
- 6 或 cancelled：已取消

---

### 2.2 会诊-专家关联表（建议表名：`mdt_consultation_expert`）

多对多：一条会诊单对应多位专家，一位专家可参与多条会诊。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | BIGINT AUTO_INCREMENT | 主键 |
| consultation_id | BIGINT | 会诊单 ID |
| doctor_id | BIGINT | 专家 ID（关联 real_doctor.doctor_id） |
| sort_order | INT | 展示顺序（可选） |
| create_time | DATETIME | 创建时间 |

**建议索引**：`consultation_id`、`doctor_id`。

说明：专家姓名、职称、医院、擅长等可直接通过 `doctor_id` 关联 `real_doctor` 查询，无需在此表冗余（若需冗余可再加字段）。

---

### 2.3 会诊病历附件表（建议表名：`mdt_consultation_attachment`）

前端有「病历附件」上传区，建议单独表存储，便于按会诊单管理、扩展类型与大小。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | BIGINT AUTO_INCREMENT | 主键 |
| consultation_id | BIGINT | 会诊单 ID |
| file_url | VARCHAR(500) | 文件访问 URL（OSS/本地路径） |
| file_name | VARCHAR(200) | 原始文件名 |
| file_size | BIGINT | 文件大小（字节） |
| file_type | VARCHAR(50) | MIME 或扩展名（如 image/jpeg） |
| sort_order | INT | 展示顺序 |
| create_time | DATETIME | 上传时间 |

**建议索引**：`consultation_id`。

若暂时不做文件上传，可先只建主表与专家关联表，附件表后续再加。

---

### 2.4 与现有表的关系

- `mdt_consultation.user_id` → `t_user`（或当前项目的用户主键）
- `mdt_consultation_expert.doctor_id` → `real_doctor.doctor_id`
- 科室筛选：专家列表可继续用 `real_doctor` 的科室/专业字段（如 `department_name`、`specialty`）查询，无需为会诊单独建科室表

## 三、后端实现建议

### 3.1 分层与命名

- **实体**：`MdtConsultation`、`MdtConsultationExpert`、`MdtConsultationAttachment`（若做附件）
- **Mapper**：MyBatis-Plus，对应 XML 中写复杂查询（如分页列表带状态筛选）
- **Service**：`IMdtConsultationService` / `MdtConsultationServiceImpl`，内部组单、算费、写主表+专家表+附件表
- **Controller**：如 `MdtConsultationController`，只做参数校验与调用 Service

注意：现有 `IConsultationService` 为「在线问诊/AI 对话」用，会诊建议用新名称（如 MdtConsultation）避免混淆。

### 3.2 核心接口建议

| 接口 | 方法 | 说明 |
|------|------|------|
| 提交会诊申请 | POST /api/mdt-consultation/submit | 入参：类型、表单字段、专家 ID 列表、附件 URL 列表（若已上传）；内部生成 order_no、算费、落库主表+专家表+附件表，返回 order_no 与总费用 |
| 会诊单列表（用户端） | GET /api/mdt-consultation/my-list | 分页，按 user_id 过滤，按 create_time 倒序；返回摘要（单号、类型、状态、总费用、创建时间、专家人数等） |
| 会诊单详情 | GET /api/mdt-consultation/detail/{id} 或 ?orderNo=xxx | 返回主表信息 + 专家列表（含 real_doctor 展示字段）+ 附件列表，用于「我的会诊」详情页 |
| 专家列表（按科室） | GET /api/real-doctor/list | 已有；可增加参数 department 或 specialty，与前端「选择专家」步骤的科室筛选一致 |
| 费用计算（可选） | GET 或 POST /api/mdt-consultation/calculate-fee | 入参：会诊类型、专家数量；返回 baseFee、extraFee、totalFee，便于前端在「确认提交」前展示与校验 |

支付、取消、状态变更（如「待排期→已排期」）可后续按业务再加接口。

### 3.3 提交接口入参 DTO 建议

与前端步骤 1～4 对应，建议 DTO 包含：

- `consultationType`: String 或 Integer（online/offline 或 1/2）
- `diseaseType`, `conditionDesc`, `pastHistory`, `treatmentPlan`, `consultPurpose`, `expectedTime`, `contactPhone`
- `expertDoctorIds`: List&lt;Long&gt;（专家 ID，对应 real_doctor.doctor_id）
- `attachmentUrls`: List&lt;String&gt;（可选，若前端先上传再提交）

费用可在后端按「基础费 + (专家数-1)×加价」重新计算并写入 `total_fee`，避免前端篡改。

### 3.4 安全与权限

- 提交、我的列表、详情均需**登录**，从 token/session 取 `userId`，不要信任前端传的 user_id。
- 详情接口需校验：当前用户只能查自己的会诊单（或管理员可查全部）。

## 四、小程序端实现建议

### 4.1 与后端对接

- **提交**：在「确认提交」时调用 `POST /api/mdt-consultation/submit`，把当前步骤 1～4 的数据（类型、表单、专家 ID 列表）按 DTO 格式传；若先做附件上传，则把返回的 URL 列表一并传。
- **列表**：在「我的会诊」页调用 `GET /api/mdt-consultation/my-list`，分页加载，展示单号、类型、状态、费用、时间等。
- **详情**：点击某条会诊单进入详情页，调用 `GET /api/mdt-consultation/detail?id=xxx`，展示完整信息、专家列表、附件列表。
- **专家选择**：步骤 3 的专家列表改为请求 `GET /api/real-doctor/list`，科室筛选用现有或扩展的科室参数；选择结果只传 `doctor_id` 列表即可。

### 4.2 病历附件上传

- 前端：使用 `uni.chooseImage` / `uni.uploadFile`（或项目内已有上传封装），先上传到后端或 OSS，拿到 `file_url` 再在提交时传给后端。
- 后端：提供「上传接口」返回 URL，或直传 OSS 时由后端返回可访问 URL；保存到 `mdt_consultation_attachment`。
- 限制：与前端一致，最多 10 张；可限制大小（如每张 5MB）和格式（如仅图片/PDF）。

### 4.3 新增页面建议

- **我的会诊列表**：路径如 `pages/medical-service/consultation-list.vue`，从管理页「会诊」入口进入后，可增加「我的会诊」入口跳转该列表；列表项可点进详情。
- **会诊详情**：路径如 `pages/medical-service/consultation-detail.vue`，展示状态、疾病信息、会诊目的、专家团队、附件、费用、预计/实际时间等；若支持「取消」或「去支付」，可在此页放按钮并调对应接口。

### 4.4 状态与用户提示

- 在列表和详情中**明确展示状态**（待审核、待支付、待排期、已排期、已完成、已取消），并用不同颜色或标签区分。
- 关键节点可配合消息/订阅通知（如「会诊已排期，时间：xxx」），提升可预期性和信任感。

## 五、有利于用户使用的设计建议

1. **流程与当前前端一致**  
   保持「选择类型 → 填写信息 → 选择专家 → 确认提交」四步，减少学习成本；后端接口与前端步骤一一对应即可。

2. **费用透明**  
   在确认页展示「基础费用 + 专家加价」明细（与前端现有逻辑一致），提交前再次展示总价；后端校验并重算费用，避免前后端不一致。

3. **会诊单号与可追溯**  
   每条会诊生成唯一 `order_no`，列表和详情都展示；用户可凭单号咨询客服或后续复诊引用，有利于信任和复购。

4. **专家信息权威**  
   专家来自 `real_doctor`，展示职称、医院、擅长等；在「选择专家」步骤可展示简要介绍或跳转医生详情页（现有医生详情页可复用），帮助用户做选择。

5. **附件与病历**  
   支持上传病历、检查报告、影像资料，并限制数量与大小，避免误操作；列表中可展示「已附 x 张」，详情页可预览或下载，方便专家侧查看。

6. **状态与提醒**  
   状态清晰、可预期；重要状态变更配合消息提醒（如待支付、已排期、已完成），减少用户反复打开小程序查看。

7. **草稿与二次编辑（可选）**  
   若产品需要，可支持「保存草稿」：未支付前允许用户修改部分信息（如期望时间、附件），接口上可设计为「更新会诊单」或「草稿保存」，提升完成率。

8. **线下会诊的扩展**  
   若线下会诊需选择院区/地点，可在主表增加 `hospital_id`、`address` 等字段，前端在「选择类型」为线下时多一步选点；表结构预留即可。

---

## 六、实施顺序建议（不修改代码，仅作顺序参考）

1. **库表**：建 `mdt_consultation`、`mdt_consultation_expert`；如需附件再建 `mdt_consultation_attachment`。
2. **后端**：实体 + Mapper + Service + Controller；先实现提交、我的列表、详情；费用在提交时内部计算。
3. **前端**：会诊申请页对接提交接口；新增「我的会诊」列表与详情页并对接接口；步骤 3 专家列表改为接口数据。
4. **附件**：后端上传接口 + 附件表；前端上传组件与提交时传 URL。
5. **状态与通知**：完善状态流转与（可选）消息/订阅提醒。
6. **优化**：草稿、取消、支付、线下选点等按产品需求迭代。

---

以上建议可直接用于会诊表设计和小程序会诊功能实现规划；若需要某一部分的建表 SQL 示例或接口路径命名与现有项目完全统一的示例，可在此基础上再细化一版。
